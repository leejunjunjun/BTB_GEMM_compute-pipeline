HandS · Compute / Memory 공동 논의 자료

무엇을 쌓아 둘 것인가: 입력 버퍼와 누산기 복제

우리 가속기는 계산보다 메모리에서 데이터를 가져오는 데 시간을 더 많이 씁니다. 한 번 가져온 데이터를 다시 쓰려면 칩 안 어딘가에 쌓아 둬야 하는데, 쌓는 자리는 두 가지입니다. 이 페이지에서는 기본 RTL과 같은 방식으로 행렬 곱셈을 돌려 보면서 두 방식을 비교합니다.

1 · 무엇을 계산하나

매 사이클 A의 열 4개와 B의 행 4개를 외적해서 누산기 16개에 더합니다

기본 설계(operand_loader + mac_array)는 한 사이클에 이렇게 움직입니다. A의 k번째 열에서 4개(4행)를 읽고, B의 k번째 행에서 4개(4열)를 읽습니다. 둘을 서로 곱하면 4 × 4 = 16개의 곱이 나오고, 이를 누산기 16개에 하나씩 더합니다.

k를 0부터 K−1까지 반복하면 C의 4×4 타일 하나가 완성됩니다. 그다음 gemm_control이 옆 열 타일로, 열이 끝나면 아래 행 타일로 넘어갑니다(행 → 열 → k 순서).

공식 벤치마크 64×128×128에서는 C가 16 × 32 = 512타일이고, 타일마다 128단계를 거치니 모두 65,536단계입니다. 메모리는 한 번에 1바이트씩, 요청을 하나씩만 받으므로 몇 번 읽느냐가 전체 시간을 거의 결정합니다.

PE 배열 4×4사이클마다 곱 16개를 만들어 누산기 16개에 더합니다.
메모리 인터페이스요청 1개에 1바이트, 동시에 한 요청만 처리합니다.
입력 버퍼 (A/B reuse buffer)읽어 온 A, B 조각을 다시 쓰려고 보관합니다. Memory 팀 담당입니다.
누산기 / psum 저장누산 중인 타일의 중간 합을 보관합니다. 누산기는 PE 안의 FF이고, k-outer와 K 묶음은 중간 합을 별도 psum 메모리(BRAM)에 넣었다 꺼냅니다. Compute 팀 담당입니다.
2 · 시뮬레이터

계산 순서와 쌓아 둘 자리를 바꿔 가며 돌려 보기

그림의 네모 한 칸은 원소 하나입니다. 세로로 4칸 묶인 것이 A 조각, 가로로 4칸 묶인 것이 B 조각, 4×4 묶음이 C 타일입니다. 행렬 크기를 바꾸면 같은 루프를 그 크기로 다시 돌립니다. 큰 크기는 칸이 작아지니, 움직임을 보려면 작은 크기로, 숫자를 보려면 공식 벤치마크 크기로 보세요.

그룹 루프 (Set 3)
B 버퍼에 들어가는 만큼(G = B 버퍼 칸 수 / K) 열 타일을 한 묶음으로 잡고, 그 묶음을 모든 행 타일이 다 쓴 다음 다음 묶음으로 넘어가는 순서입니다. 묶음의 B는 버퍼에서 계속 재사용되어 B를 한 번만 읽지만, 묶음이 바뀔 때마다 A를 다시 읽습니다. 그림에서 점선이 묶음 경계입니다. Set 3은 G가 2보다 작거나, 묶음 하나에 열 타일이 다 들어가거나, M이 4 이하(행 타일 1개)이면 묶지 않고 Set 2 순서로 돕니다.
fixed / flexible buffer
fixed buffer는 타일 하나에 최대 K(1,024칸) 크기 자리를 잡아 K가 짧으면 남는 칸을 비워 둡니다. flexible buffer는 타일을 K 길이로 이어 붙여, 4 KB에 1024 / K개 타일이 들어갑니다. fixed A 버퍼(4 KB)는 행 타일 1개 자리뿐이라 새 행 타일이 오면 덮어씁니다. flexible A 버퍼는 지금 쓰는 칸을 뺀 남는 칸에 앞쪽 행 타일을 끝까지 남겨 두어, Set 3에서 묶음이 바뀔 때 그만큼 A를 다시 읽지 않습니다. 같은 BRAM이면 flexible이 손해가 없으므로 이 페이지의 비교는 A, B 모두 flexible buffer를 기준으로 합니다. fixed buffer는 A, B 주소 방식에서 골라 비교해 볼 수 있습니다.
누산기 세트와 방향
누산기 n세트는 출력 타일 n개를 동시에 누산합니다. B 방향은 행 타일 n개가 B 조각 하나를 같이 쓰고(B 재읽기 감소, A 버퍼에 행 타일 n개 필요), A 방향은 열 타일 n개가 A 조각 하나를 같이 씁니다(A 버퍼가 있으면 효과 없음).
메모리 / 버퍼 / staging
MAC 연산마다 A 조각과 B 조각이 어디서 왔는지를 바이트로 셉니다. staging은 지금 k 단계에서 이미 읽어 레지스터에 들고 있는 조각을 다음 연산에 그대로 쓴 경우로, 누산기를 여러 세트 쓰거나 k-outer일 때 같은 조각이 연달아 쓰이면 생깁니다. 버퍼는 A·B 버퍼에서 꺼낸 경우이고, 메모리는 새로 읽은 경우입니다. 세 값의 합은 연산에 들어간 A(또는 B) 전체 바이트입니다.
k-inner / k-outer
k-inner는 타일 하나를 k = 0…K−1까지 끝내고 다음 타일로 갑니다(기본 RTL). k-outer는 k 하나를 모든 타일에 더하고 다음 k로 가서 입력을 다시 읽지 않는 대신 모든 타일의 중간 합을 들고 있습니다.
K 묶음
출력을 행 타일 BH개 × 열 타일 BW개 블록으로 나누고, 블록마다 K를 Kc씩 끊어 누산합니다. 묶음 하나에 쓰는 A(BH × 4 × Kc 바이트)와 B(Kc × BW × 4 바이트)를 청크 버퍼에 담아 블록 안에서 다시 쓰고, 묶음 사이의 중간 합은 psum 메모리(BH × BW × 64 바이트)에 넣었다 꺼냅니다. A 읽기 = M·K·⌈C/BW⌉, B 읽기 = N·K·⌈R/BH⌉로 K와 상관없이 블록 크기로 정해집니다. Kc = K이면 psum 없이 k-inner와 같고, 블록이 행렬 전체이고 Kc = 1이면 완전 k-outer입니다. 그림의 점선이 블록 경계이고, 보라 테두리 타일은 psum 메모리에 보관 중인 타일입니다.

A 조각 (세로 4칸, 한 번 이상 읽음) B 조각 (가로 4칸) 붉을수록 여러 번 다시 읽음 (확대하면 칸에 읽은 횟수가 숫자로 표시) 지금 버퍼에 들어 있음 누산 중인 타일 (4×4)psum 메모리에 보관 중 (K 묶음) 완성된 타일 옅은 칸 = 마스크로 꺼진 자리 (4로 안 나눠떨어질 때)

B 버퍼는 실제 하드웨어 크기(KB)로 고릅니다. Set 2는 16 KB, Set 3은 4 KB이고, Set 3의 묶음 크기 G는 1024 / K로 정해집니다. 진행 단계 하나는 MAC 연산 한 번이며, 연산 한 번에 걸리는 시간은 메모리 읽기에 따라 달라서, 64×128×128에서 Set 2는 약 2사이클, 원래 설계는 약 23사이클입니다(모델, lat 1). A 버퍼도 크기로 고릅니다. 한 칸(4바이트)에 A 조각 하나가 들어가며, Set 1~3은 1,024칸(4 KB, 칸마다 zero 플래그 1비트 별도), Memory 팀 슬라이드의 A cache는 128칸(0.5 KB)입니다. 누산기를 B 방향으로 n세트 쓰면 행 타일 n개분(n × K칸)이 필요하고, 모자라면 모자란 만큼 열 타일마다 A를 다시 읽습니다. 오른쪽 패널의 버퍼 크기는 설정한 하드웨어 크기이고, A의 \"필요\"는 그 설정이 실제로 쓰는 양입니다.

3 · 바로가기

주의해서 볼 케이스

공동 논의에 필요한 비교 7개만 먼저 보여 줍니다. 모두 A, B 버퍼를 flexible buffer로 둔 경우이고, 순서대로 Set 2 기준점, Set 3, 그 위에 누산기 8세트를 더했을 때의 추가분(K = 128, 512), Compute 팀 Idea 1, 큰 K의 한계와 그 대안인 K 묶음입니다. fixed buffer와 비교하는 카드는 “나머지 케이스”에 있습니다. 누르면 행렬 크기와 방식이 한 번에 설정되고 시뮬레이터로 이동합니다. 메모리 지연 23 카드는 지연 선택도 함께 바뀝니다. 끝난 상태로 열리며, 재생을 누르면 처음부터 다시 돕니다. 시간은 lat 1 기준입니다.

계산 방식. 모든 설정의 시간을 같은 방식으로 계산합니다. 먼저 이 페이지의 루프 코드로 메모리 읽기 바이트를 세고, 그다음 사이클 = 1.161 × MAC 연산 + (메모리 지연 + 1.76) × 읽기 바이트 + psum 꺼내기·저장을 적용합니다. psum 항은 K 묶음과 완전 k-outer에만 있고, 타일 하나를 꺼내거나 저장할 때 512비트 포트면 1사이클, 32비트 포트면 16사이클로 셉니다. 완전 k-outer는 512비트 포트로 둡니다. 두 계수는 공식 testbench(tb_gemm.sv, Icarus)에서 Set 2/3을 64×128×128로 돌린 결과(메모리 지연 1, 23)에 한 번 맞춘 값이고, 그 결과들과는 0.3% 안쪽으로 맞습니다.

평가 기준. 공식 평가는 실행 시간(사이클 × 클럭 주기)입니다. 클럭 주기는 아직 정해지지 않아서 이 페이지는 사이클만 비교합니다. 누산 경로를 나누는 등 클럭을 올리는 변경의 효과는 여기에 나타나지 않습니다.

검증과 한계. 읽기 바이트는 공식 testbench 크기 7개에서 원래 설계와 Set 1, Set 2의 실측 읽기와 정확히 일치합니다. 시간은 실측보다 원래 설계와 Set 1 같은 로더에서 약 11~13%, 아주 작은 행렬에서는 고정 오버헤드만큼 짧게 나옵니다. 모든 설정이 같은 식을 쓰므로 설정끼리의 비교는 일관되지만, 절대 사이클은 실측과 다를 수 있습니다. psum 꺼내기·저장은 MAC과 겹치지 않는다고 가정해 그대로 더하므로, 이중 버퍼로 겹칠 수 있다면 K 묶음과 k-outer의 시간은 상한입니다. psum의 BRAM36 개수는 포트 폭으로 정해집니다(512비트는 깊이 512마다 8개, 32비트는 1,024워드마다 1개). zero skip(희소 데이터), 결과 쓰기 대기, k-outer와 K 묶음의 마지막 결과 배출은 모델에 없고, K 묶음은 실측으로 검증하지 않았습니다.
